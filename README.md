# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из `migrations/` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume.

## Swagger

Swagger UI:

```text
http://localhost:8080/swagger/
```

OpenAPI JSON:

```text
http://localhost:8080/swagger/openapi.json
```

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST   /api/v1/tasks`
- `GET    /api/v1/tasks`
- `GET    /api/v1/tasks/{id}`
- `PUT    /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Реализованная фича: периодичность задач

### Общее

Каждая задача может иметь необязательное расписание (`schedule`). Расписание передаётся вложенным объектом в теле запроса. Если `schedule` не указан или равен `null` — задача разовая, поведение не меняется.

### Типы расписаний

| Тип        | Описание                                  | Обязательные поля    |
|------------|-------------------------------------------|----------------------|
| `daily`    | Каждые N дней                             | `interval` (≥ 1)     |
| `monthly`  | Каждое N-е число месяца                   | `day_of_month` (1–30)|
| `specific` | Только на конкретные даты                 | `dates` (≥ 1 даты)   |
| `parity`   | Чётные или нечётные дни месяца            | `parity` (even/odd)  |

### Примеры запросов

**Создать ежедневную задачу (каждые 2 дня):**
```json
POST /api/v1/tasks
{
  "title": "Ежедневный обзвон пациентов",
  "status": "new",
  "schedule": {
    "type": "daily",
    "interval": 2
  }
}
```

**Создать ежемесячную задачу (15-го числа):**
```json
POST /api/v1/tasks
{
  "title": "Ежемесячная инвентаризация",
  "status": "new",
  "schedule": {
    "type": "monthly",
    "day_of_month": 15
  }
}
```

**Создать задачу на конкретные даты:**
```json
POST /api/v1/tasks
{
  "title": "Подготовка к конференции",
  "status": "new",
  "schedule": {
    "type": "specific",
    "dates": ["2026-04-10", "2026-04-20"]
  }
}
```

**Создать задачу на чётные дни:**
```json
POST /api/v1/tasks
{
  "title": "Формирование отчётности",
  "status": "new",
  "schedule": {
    "type": "parity",
    "parity": "even"
  }
}
```

**Удалить расписание при обновлении** (передать `schedule: null` или не передавать поле):
```json
PUT /api/v1/tasks/1
{
  "title": "Разовая задача",
  "status": "in_progress"
}
```

### Структура ответа с расписанием

```json
{
  "id": 1,
  "title": "Ежедневный обзвон",
  "description": "",
  "status": "new",
  "schedule": {
    "id": 1,
    "type": "daily",
    "interval": 2
  },
  "created_at": "2026-04-10T09:00:00Z",
  "updated_at": "2026-04-10T09:00:00Z"
}
```

## Архитектурные решения и допущения

### Отдельная таблица `schedules`

Расписание хранится в отдельной таблице, связанной с `tasks` через `task_id` (1:1). Альтернатива — JSONB-колонка в `tasks`. Выбрана отдельная таблица, потому что:
- Структура расписания достаточно сложная с несколькими взаимоисключающими полями.
- Отдельная таблица допускает индексирование и будущие запросы типа "все задачи с ежемесячным расписанием".

### Семантика PUT (полная замена)

PUT `/tasks/{id}` полностью заменяет задачу и её расписание:
- Если `schedule` указан — создаётся или заменяется.
- Если `schedule` не указан или `null` — расписание удаляется.

Это соответствует REST-семантике PUT как полного обновления ресурса.

### Допущение: `day_of_month` ограничен 30

Значение `day_of_month` принимается в диапазоне 1–30. Значение 31 намеренно исключено, так как таких дней нет в феврале, апреле, июне и других коротких месяцах. Если указанного числа нет в текущем месяце (например, 30 февраля) — предполагается, что клиент использует последний день месяца.

### Допущение: хранение дат в формате YYYY-MM-DD

Даты для типа `specific` хранятся как массив строк (`TEXT[]`) в формате `YYYY-MM-DD`. Это упрощает код и избегает проблем с часовыми поясами — у задач нет понятия "время дня".

### Транзакции при создании и обновлении

Создание и обновление задачи + расписания выполняются в одной транзакции. Если вставка расписания упадёт — задача тоже не создастся.
